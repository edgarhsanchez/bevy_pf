## Tier 1 â Quick wins (<1 day each)

Ranked by warnings eliminated per effort. File references are to `/Volumes/MoreSpace/Documents/github/bevy_pf/crates/bevy_pf/src/`.

**1. `ElementName` bindings.** The single biggest warning source: ~130 uses in Gallery alone (the dominant Gallery binding form â every demo page's interactive knobs), plus Inventory/Login. Infrastructure already exists: `binding.rs` parses then rejects it via `BindingSpec.unsupported` (field doc at line ~255, `parse_binding_extension` at 261), and the `XamlNames` registry on the scene root already maps namesâentities. Change: add `element_name: Option<String>` to `BindingSpec`; in the binding-resolution system, when set, resolve source via `XamlNames` and read/write the target element's bindable properties (start with `Value` (Slider), `IsChecked`, `Text`, `SelectedItem`, `Foreground`, `ActualWidth/Height` read-only) instead of `DataContext`. Poll-on-change using the same version-diff loop you use for `Bindable`. This flips ~15 Gallery pages from "degraded" to "functional".

**2. Viewbox.** 14+ sample files; one of the three cheapest gaps blocking the most content (per gallery analyst). Add to `ElemKind::from_name` (instantiate.rs:101â129). MVP: single-child container; post-layout system compares child's measured size to Viewbox's laid-out size and applies a uniform `UiTransform` scale (you already have `convert::ui_transform`, instantiate.rs:1033â1043). Support `Stretch=Uniform` (default) + `Fill`; warn on `StretchDirection` for now.

**3. `{x:Static}` for enum values + `sys:` primitives.** Noesis itself only supports x:Static for *enums, routed commands, and DP defaults* â so enum-only is compatibility-correct and cheap. Handle in the markup-extension resolution path (instantiate.rs `resolve` around line 706â790): parse `{x:Static Visibility.Visible}` â strip type qualifier â feed the member name to the existing enum converter. Add `sys:String/Double/Int32/Boolean` beside the existing `x:Double`/`x:String` in `resources.rs` (~line 178). Counts: 29/11 x:Static in themes, `sys:String` ComboBox items across TextBlock/ComboBox/Menu3D/TicTacToe pages.

**4. `Panel.ZIndex` / `Canvas.ZIndex`.** Attached-property handler in instantiate.rs â insert bevy `ZIndex`. Needed by Canvas.xaml overlap demo and theme templates (Windows uses it). Trivial.

**5. RenderTransform from strings + transform elements everywhere.** instantiate.rs:1033 currently errors unless the value is already `PfValue::Transform`. Add: (a) matrix-string converter (`RenderTransform="1,0,0,1,20,20"`) â Touch sample's 16-line MainWindow is the ready oracle; (b) `TranslateTransform/ScaleTransform/RotateTransform/SkewTransform/TransformGroup` element parsing into `PfValue::Transform` if not complete; (c) honor `RenderTransformOrigin` (currently in the ignore list at line ~1121) since `UiTransform` supports an origin-equivalent. 20+ sample files use transforms; 70 RenderTransforms in Windows.xaml theme.

**6. Foreign-namespace (`noesis:`, `b:`, `d:`-extension) graceful skip + `noesis:Text.Placeholder`.** Verify unknown-prefix attributes and property elements skip with *one* warning class (so the histogram groups them), then actually implement `Text.Placeholder` on TextBox â you have native `EditableText`; placeholder is a ghost TextBlock toggled on empty. 8 uses in ThemePreview, plus Gallery TextBox page.

**7. Qualified setter property names + `BasedOn="{x:Null}"`.** In `resources.rs` setter parsing (~line 500â600): strip `Control.`/`FrameworkElement.` qualifiers from `Setter Property="Control.Background"` (Nocturnal's root style feeds **59** BasedOn references â without this, all of Nocturnal's styles break), and treat `BasedOn="{x:Null}"` as "no base" instead of an error (7 uses in Windows.xaml). Also make setters for properties absent on the target a warning, not a failure (theme T4 semantics).

**8. WrapPanel `ItemWidth/ItemHeight`, UniformGrid `FirstColumn`, DockPanel `LastChildFill`.** Small layout-parameter gaps flagged unverified/ignored (LastChildFill is in the ignore list, instantiate.rs:1119). ## Tier 2 â Structural (multi-day), in recommended order

**2.1 URI model + `ResourceDictionary Source=` + MergedDictionaries + application resources.** Do this first: it unblocks *every* Noesis sample app (App.xaml â Resources.xaml â MainWindow.xaml) and all theme loading, and everything later (templates, fonts, images, sounds) consumes it. Implement: canonical `PfUri { scheme, assembly, path }` accepting all five spellings (relative, `/root-relative`, `/Asm;component/path`, `pack://application:,,,/...`, `file:`); baseUri threaded through the parser so every nested load resolves relative to *its containing file*; `Source=` triggering recursive dictionary load with a cycle guard; merged lookup = own keys first, then merged dictionaries last-to-first; a process-global app dictionary installed **before** any view instantiates (mirror `GUI::SetApplicationResources`), added as the fallback tier after the lexical scope chain in `resources.rs`. **Key decision:** map `assembly` to bevy `AssetSource` namespaces so `/MyLib;component/...` routes to a different provider â one URI namespace shared across XAML/texture/font/audio, exactly like Noesis's provider registry. Also split `FontFamily` on `#` into (folder-URI, family name).

**2.2 Binding infrastructure upgrade: property-name granularity, `ObservableCollection`, commands.** Prereq for templating and for scale. (a) Keep `Bindable`'s version counter as coarse filter but add a drained `SmallVec` of changed property names so invalidation is O(affected) not O(bindings) â this is what `OnPropertyChanged(name)` buys Noesis. (b) `#[bindable]` derive generating equality-check+notify setters (better than Noesis's hand-written idiom). (c) `PfCommand` (execute + can_execute + changed event) bindable via `Command=`/`CommandParameter=` â every interactive Noesis sample uses it. (d) `ObservableList<T>` emitting granular add/remove/reset events. **Key decision:** changed-name set beside the version counter, not replacing it â pull stays the fallback for plain `Reflect` view-models.

**2.3 `ItemsSource` + DataTemplate + ItemsPanelTemplate.** The gate to every data-driven game screen (QuestLog, Scoreboard, Inventory). **Key decision:** store templates as *unexpanded* `XamlNode` subtrees (keyed resources or inline), instantiated per item through the existing `instantiate.rs` path with the item as `DataContext`; diff the collection via 2.2(d) events, mapping index ops to child-entity ops. `ItemsPanelTemplate` swaps the items-host `ParentKind`. Defer `DataTemplate.Triggers` to 2.6.

**2.4 Popup/overlay layer + ComboBox, ToolTip, ContextMenu, Menu.** One shared mechanism: a global overlay root entity with high `GlobalZIndex`; a `PfPopup` component (placement target entity, `Placement`, `IsOpen`) positioned post-layout from the target's computed rect. ComboBox = ToggleButton + ListBox-in-popup (its dropdown reuses 2.3's items machinery); ToolTip = hover-timer + popup; Menu/ContextMenu = nested popups. ComboBox alone is used as the "demo knob" on 15+ Gallery pages, so it multiplies oracle coverage. **Key decision:** popups are reparented under the overlay root but keep a logical-parent link for DataContext/resource/font inheritance â inheritance must follow the logical tree, not the entity tree.

**2.5 Transforms consolidation via `UiTransform`.** Finish what T1 started: full `TransformGroup` composition order, `CompositeTransform` shorthand, animate-ready storage (each transform as a struct you can retarget by indexed path later, e.g. `RenderTransform.Children[0].X` â Storyboards in Tier 3 target these). **Key decision:** `RenderTransform` â `UiTransform` post-layout (does not affect layout â matches WPF); `LayoutTransform` stays warn-and-ignore (Noesis samples barely use it).

**2.6 `Style.Triggers`: property Trigger + DataTrigger + MultiTrigger, and a value-provider store.** This is the load-bearing design decision of the whole roadmap. Introduce a per-entity property store where each settable property records values from prioritized providers (local > animation > template-trigger > style-trigger > style-setter > inherited > default â WPF precedence), and effective-value recomputation on provider change. Triggers watch source properties (`IsMouseOver` from `Interaction`, `IsChecked`, bound data values) and push/pop setter values as a provider layer. Counts: `<Trigger>` 124/82/171 across the three themes; DataTriggers are the backbone of every game sample (36 in TicTacToe). **Key decision:** build the store *now*, sized for triggers only, but with the provider-priority enum already including Animation and TemplatedParent slots â Storyboards and templates then plug in without another refactor. (Bonus: it directly enables a Noesis-Inspector-style "who set this value" debug view.)

**2.7 ControlTemplate groundwork.** With 2.1 (resources), 2.6 (providers), and 2.3 (template = stored XamlNode subtree) in place, ControlTemplate is: expand the keyed/inline template subtree under the control at instantiate time, stamping each spawned entity with `TemplatedParent(Entity)`; `TemplateBinding X` = one-way binding whose source is the templated parent's property store (123/357/138 uses in themes); `ContentPresenter` resolves `Content`/`ContentSource="Header"` from the templated parent; template triggers use `TargetName` resolved against a template-scoped namescope (separate from `XamlNames`); recognize `PART_*` names and let control logic look them up. **Key decision:** template namescopes are per-expansion and isolated â never merge template `x:Name`s into the page-level registry.

## Tier 3 â Long horizon

**Storyboard/animation.** Fits instantiate.rs's model as data: parse `Storyboard`/`*Animation(UsingKeyFrames)` elements into a `PfValue::Storyboard` clip description (target name, property path, keyframes, easing) stored like any keyed resource; a `PfStoryboardPlayer` component on the triggering entity holds active clips + start times, and one system per frame samples clocks and writes results into the Tier-2.6 value store at Animation priority â never touching components directly, so `HandoffBehavior`/revert-on-stop falls out of provider push/pop, exactly like trigger Enter/ExitActions (180 `Trigger.EnterActions` in Windows.xaml). Property paths reuse the binding reflection-path code plus indexed Freezable paths (`(Border.Background).(GradientBrush.GradientStops)[0].(GradientStop.Color)`) â support Double, Color, Thickness, Point, Object keyframes first (those cover 95% of theme/sample usage), easing via `bevy_math` curves (11 easing functions, Discrete/Linear/Spline keyframes). `EventTrigger`+`BeginStoryboard` and the `b:` behavior actions (`ControlStoryboardAction`, `ChangePropertyAction`, `PlaySoundAction`) are thin drivers over the same player â and they, not code-behind, are what make Noesis XAML "game UI" (thousands of keyframes across the game samples).

**VisualStateManager.** VSM is a disciplined faÃ§ade over Storyboards: `VisualStateGroups` attach to a template root; each `VisualState` holds one Storyboard; `GoToState` stops the group's previous state's storyboard and begins the new one, with `VisualTransition GeneratedDuration` synthesizing a linear tween between the two states' final provider values (188 transitions in Nocturnal). Implementation: a `PfVisualStates` component on the templated root storing groupâcurrent-state; controls call `go_to_state(world, entity, "MouseOver")` from the same interaction systems that drive triggers today; generated transitions are synthesized clips fed to the Tier-3 animation player. Since Nocturnal is the only theme that needs VSM and it needs it pervasively (179 VisualStates), gate "Nocturnal loads" as the acceptance test; Agile/Windows validate the trigger-only path independently.

**Full template system / theme parity.** The end-state: default templates for every control shipped as a bevy_pf theme dictionary (mirroring `NoesisTheme.Styles.xaml`'s single shared style sheet), implicit-style application consulting element scope â app resources â embedded debug theme, `OverridesDefaultStyle`, `FocusVisualStyle`, and the `PART_` contract formalized as a trait (`fn on_template_applied(&mut self, parts: &NameScope)`) so control behavior (TextBox caret host = `PART_ContentHost`, ProgressBar fill = `PART_Indicator`, Slider/ScrollBar `<Track>` with Decrease/Thumb/Increase children) binds to whatever template the user supplies. This is where `ElemKind`'s hardcoded visual construction inverts: `insert_defaults` becomes "apply the theme's template," and today's hand-built chrome becomes the embedded fallback theme â rendered **pink**, per Noesis, so an unthemed control is unmissable. Acceptance oracle: load Agile.xaml (simplest full theme: no VSM, no MultiTrigger, only 25 brushes) end-to-end, then Windows.xaml (storyboard-heavy), then Nocturnal (VSM + layered ColorâRampâBrush resources with StaticResource inside Freezables â 212 such refs).

## Style-testing strategy

All tests authored from scratch (no SDK content copied); patterns only.

**Core five (theme-derived), as integration tests instantiating XAML strings against a headless `World`:**
1. **Layered resource composition** â Color â GradientStopCollection (stop uses `{StaticResource}` to the color) â Brush (`GradientStops="{StaticResource ...}"`) â implicit Button style. Assert final gradient stop color; pin forward-reference behavior (Noesis allows forward refs â decide and document ours).
2. **Implicit style + template + TemplateBinding round trip** â style sets Padding/BorderThickness/Template; assert Border thickness flows styleâTemplateBinding, local `Padding="9"` beats the style setter, ContentPresenter shows content with no explicit binding. (Tier 2.7 gate.)
3. **Template triggers with TargetName + precedence-correct revert** â hoverâpressâreleaseâunhoverâdisable sequence; assert the named part's background at each step and that the no-TargetName Foreground setter styles the control itself and reverts. (Tier 2.6 gate; directly tests the value-provider store.)
4. **BasedOn with qualified setters + `BasedOn="{x:Null}"`** â untyped base style with `Control.Padding`; derived CheckBox/Button styles; assert inheritance, override, null-opt-out, and that an inapplicable setter warns instead of failing. (Tier 1 item 7 gate.)
5. **Resource scoping + per-subtree theme override** â app-dictionary brush + implicit style vs. a panel-local dictionary redefining both; assert nearest-scope wins, and pin Static (resolved-at-load, stays) vs. Dynamic (re-resolves when the inner dictionary is removed). Per-subtree theming is Noesis's *standard* skinning pattern, so this must be rock solid.

**Additions suggested by docs/gallery:**
6. **Sweep-as-CI**: keep the 172-file instantiation sweep runnable against a local SDK path (env var), snapshot the warning histogram, and fail CI if any warning *category count increases*. Each Tier-1 item should land with a histogram diff in its PR description.
7. **Oracle clones**: from-scratch re-authored equivalents of the 8 ranked oracles (Grid tracks/spans/nested, Canvas L/T/R/B+ZIndex, StackPanel, a Commands-style Window with TwoWay TextBox, TextBox flags, RadioButton groups, 11-config Slider, 4-direction Expander) with layout assertions on computed rects â these test *behavior*, while the sweep tests *acceptance*.
8. **URI matrix test** (Tier 2.1): all five URI spellings + relative resolution from a nested dictionary two folders deep + `Fonts/#Family` splitting, asserting one canonical `(scheme, assembly, path)`.
9. **App-resources ordering test**: app dictionary must be queryable before `StartupUri`-equivalent view instantiation (Login pattern: MainWindow references keys defined in Resources.xaml merged by App.xaml).
10. **ElementName degradation contract**: binding to a missing name warns once and leaves the target property at its otherwise-effective value (never panics, never poisons sibling bindings).
11. **Theme-preview gallery example**: our own `examples/gallery.rs` + control-gallery XAML (ThemePreview pattern) doubling as manual regression surface and README screenshot source.

## What to steal from Noesis, design-wise

- **The pink fallback theme.** Unstyled/untemplated controls render pink. Cheapest diagnostic ever shipped; adopt the moment templates land.
- **Per-member Yes/No "Sup" compat tables.** Their `_ClassHierarchy` per-class tables are the compat oracle users actually consult. Generate ours from the test suite (doc-table â test names) so it can't go stale.
- **"Any deviation from WPF is a bug"** as the stated compat contract, with a short documented-deviations page (ours: f32 not f64, no exceptions â warnings vector, Bevy-specific roots). We already match two of their three deviations by accident; document it.
- **Errors are non-fatal, always.** Noesis never throws on bad XAML at runtime; it logs and renders what it can. `instantiate.rs`'s warnings vector is already this â protect that property in every new feature (triggers, templates, storyboards must degrade, not abort).
- **One URI namespace across asset types** (XAML/texture/font/audio share path strings and provider routing) â maps cleanly to bevy `AssetSource`.
- **Theme layering**: entry file merges `Colors.{Dark,Light}` â `Brushes.{Accent}` â `Fonts` â one shared `Styles` sheet; the inverted-semantics color trick (dark theme's "Color.Black" is light) yields 18 themes from one style sheet. Structure our future default theme this way from day one.
- **XamlPlayer**: a drag-and-drop + hot-reload standalone viewer with F5, `--log_binding` verbosity, and debug overlays (wireframe/batches/overdraw). We already have `hot_reload`; a `bevy_pf_player` example binary is mostly plumbing and becomes the designer loop.
- **Inspector's value-provider view** ("who set this property, which providers were overridden") â falls out nearly free from the Tier-2.6 provider store; expose via `bevy-inspector-egui` integration or a debug component.
- **In-process LSP/validation**: their language server runs *inside the app* so completion reflects the real registered type set â for us, a `--lang_server`-style feature on the user's own binary beats a standalone validator with stale type info.
- **Two-callback code-behind contract** (`ConnectField`/`ConnectEvent` string-matched, return-false-warns): the Rust mapping is a `XamlComponent` trait + `connect_field!`/`connect_event!` macros â no codegen, tooling-compatible with Blend-style XAML.
- **`StyleInteraction` (behaviors inside Style setters)** â Noesis's own extension beyond WPF; worth copying when behaviors land, since it's how themes attach interactivity without templates.
- **`noesis:Text.Placeholder` and gamepad/XY-focus extensions** â pragmatic game-UI gaps in WPF that Noesis filled; adopt the same attached-property names (`pf:` namespace) for ecosystem familiarity.
